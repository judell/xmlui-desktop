# Bram trace vocabulary

Consult this on-demand reference while reading `bram-trace.log` or an
Inspector export; it catalogs the trace categories, subkinds, fields, and
their diagnostic purpose without loading that Bram-internal detail into
every managed-project session.

### Grep host categories in bracketed form

`bram-trace.log` ingests PTY content: `[iframe] subkind=send-capture` records
carry the terminal's visible rows, which include the agent's own chat text. So a
bare grep for a term currently under discussion matches the **conversation about**
an instrument rather than the instrument's output.

Always grep the bracketed form — `grep '\[claim-interval\]'`, not
`grep 'claim-interval'`.

The asymmetry is what makes it dangerous: the false positives appear exactly when
you are actively discussing an instrument, which is exactly when you are most
likely to grep for it, and an inflated count reads as *"it fired"* when the truth
is *"it did not"*. It produced two wrong readings minutes apart on 2026-09-01 —
`claim-interval` counted 2 against a true 0, then `op=prune-noop` counted 2
against a true 0 — the second after the first was already understood, which is
the argument for writing it down rather than remembering it.

### Snapshot before manual hunk surgery

Splitting one file's changes between items means rewriting a file that holds
uncommitted work: reset it, apply one item's interval patch, commit, apply the
next. An interruption partway through leaves the tree in a state nobody authored.

Pin the current tree first, so nothing can be lost:

```sh
IDX=$(mktemp -u); GIT_INDEX_FILE=$IDX git read-tree HEAD \
  && GIT_INDEX_FILE=$IDX git add -A
SAFE=$(GIT_INDEX_FILE=$IDX git write-tree); rm -f $IDX
git update-ref refs/bram/safety/<name> $SAFE
```

The capture is the same temp-index tree write the claim boundaries use, so it
includes untracked files and never touches the worktree, and the ref stops gc from
reclaiming it. Afterwards, `git diff refs/bram/safety/<name> HEAD` must return
**empty** — that check is what demonstrates the commits reproduced the pre-split
state rather than approximating it. Release the ref explicitly with
`git update-ref -d` so stale safety refs do not accumulate.

`refs/bram/` now holds two namespaces, and they differ in who cleans up:

| namespace | written by | retired by |
| --- | --- | --- |
| `refs/bram/claims/*` | the host, at every claim boundary | the prune sweep, automatically |
| `refs/bram/safety/*` | you, before manual hunk surgery | you, explicitly |

`git for-each-ref refs/bram` lists both together, so a stale safety ref is
miscounted as a boundary by anyone reading the store — and nothing will ever
retire it for you.

### Reading the claim store

Three commands and one interpretation rule.

```sh
git for-each-ref refs/bram/claims          # the boundaries
cat resources/.claim-intervals.json        # ref -> ids, kind, timestamp
```

Records in the sidecar are in **insertion order**, so a boundary's predecessor is
the previous array element — not the one with the next-lowest `atMs`. That is also
what settles two boundaries landing in the same millisecond, and the prune's
adjacency rule depends on it.

Exactly **one ref** is the normal resting state rather than an error: it is the
open interval's base, which is never retirable. An **empty** store is the honest
state of a project that has never captured a boundary, and is indistinguishable
from one whose sweep never ran — the residual ambiguity `op=prune-noop`
deliberately does not close.
